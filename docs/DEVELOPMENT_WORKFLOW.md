# Development Workflow & CI Harness

## 分支开发流程

项目采用 `main + feature branch + Pull Request + CI` 的标准开发流程。

所有代码修改必须基于最新 `main` 创建独立分支完成，不直接在 `main` 上开发。

标准流程：

1. 同步最新 `main`。
2. 创建独立开发分支。
3. 在开发分支完成代码修改、测试补充和功能验证。
4. 提交 Pull Request。
5. 等待线上 CI Harness 完成全部质量检查。
6. 所有检查通过后合并到 `main`。
7. `main` 始终保持稳定、可构建、可部署状态。

---

## CI Harness 质量门禁

每个 Pull Request 必须经过自动化 Harness 验证。

Harness 负责：

- TypeScript 类型检查。
- Lint 代码规范检查。
- 单元测试执行。
- 集成测试执行。
- E2E 流程验证（适用时）。
- 生产构建验证。

未通过全部检查的 Pull Request 不允许合并到 `main`。

---

## Pull Request 要求

每个 PR 应包含：

- 清晰的问题背景。
- 实施方案说明。
- 影响范围说明。
- 测试结果。
- 关联 Issue。

推荐格式：

```text
## 问题
说明解决的问题。

## 修改
说明代码变化。

## 测试
说明本地和 CI 验证结果。

## 影响
说明兼容性和风险。
```

---

## 合并原则

只有满足以下条件才允许进入 `main`：

- CI 全部通过。
- 测试覆盖满足要求。
- 不存在未解决的重要 Review 问题。
- 文档和变更记录同步更新。

---

## 开发目标

该流程用于保证：

- 主分支长期稳定。
- 每次提交均可追踪。
- Bug 修复和功能开发均可回溯。
- 自动化检查替代人工遗漏。
- 项目持续具备发布能力。
